## Account deletion — does not exist

Grepped `src/` and `supabase/` for every plausible deletion entry point: `deleteUser`, `delete account`, `deactivate`, `admin.deleteUser`.

**Result: `supabase.auth.admin.deleteUser()` is called in exactly two places, both in `src/lib/e2e/cleanup.ts` (lines 66 and 82) — the isolated Playwright/E2E test-persona cleanup script.** That script is explicitly gated to never touch anything but synthetic E2E accounts (`isGenuineE2eUser()` requires both a `user_metadata.e2e_test === true` marker *and* an `@e2e.avela.invalid` email, and `requireIsolatedE2eBackend()` refuses to run at all if the E2E Supabase URL matches production — see `docs/security.md` Milestone 10.8). It is never imported by anything under `src/app/`.

**There is no Server Action, Route Handler, or any other app-reachable code path that lets a student — or an admin acting on a student's behalf — delete their own account today.** `docs/security.md`'s own Milestone 1 note confirms this was a deliberate design: *"No delete policy [on `profiles`] ... Rows are only removed via the `on delete cascade` from `auth.users`, which is what 'deleting your account' should actually mean"* — i.e. the schema was built expecting `auth.users` deletion to be the deletion mechanism, but that mechanism was never wired up to anything a user or admin can trigger through the product.

## FK/storage cascade map — what would happen if a user row were deleted today

Every foreign key in every migration that references `auth.users(id)` or (transitively) `public.profiles(id)` was grepped across all 24 migration files. **Every single one uses `on delete cascade`** (no `on delete restrict`, no `on delete set null` on a direct-to-user FK, and no FK left with an unspecified/default `no action` behavior was found referencing a user). Concretely, if `auth.users` row deletion were ever wired up, Postgres would automatically cascade-delete rows in, among others:

`profiles` → `student_interests`, `student_goals`, `student_opportunity_preferences` (cascade from `profiles`, not directly from `auth.users`)

Directly from `auth.users`: `saved_opportunities`, `student_discovery_runs`, `student_opportunity_recommendations`, `recommendation_feedback`, `application_plans` (→ cascades further to `application_tasks`, `application_evidence_links`), `student_reminders`, `portfolio_items` (→ cascades further to `portfolio_files`, `portfolio_verifications` → `portfolio_verification_events`, `portfolio_osint_checks` → `portfolio_osint_evidence`/`portfolio_osint_conflicts`/`portfolio_osint_review_events`, `claim_dimension_results` → `claim_dimension_events`, `identity_possession_challenges`, `verifier_domain_assessments`, `verification_field_confirmations`, `portfolio_personal_project_details` → `portfolio_possession_challenges`, `integrity_signals` (also on `portfolio_item_id`), `portfolio_entry_narrative`, `portfolio_team_details`, `portfolio_team_collaborators`, `portfolio_generic_profile_challenges`, `portfolio_review_links` → `portfolio_review_link_items`, `portfolio_confirmation_requests`), `connected_identities` → `connected_identity_events`, `integrity_signals` (also directly, and via `related_user_id`), `integrity_reviews`, `rate_limit_counters`, `user_roles`.

**Conclusion on rows: essentially nothing would be orphaned at the database level** — the schema is unusually consistent about cascading from `auth.users`, so a real `auth.users` deletion would cleanly remove every row this audit found across every table checked.

**Two things Postgres cascade structurally cannot reach, confirmed as gaps:**

1. **Supabase Storage objects in the `student-portfolio` bucket.** `docs/database.md`/`docs/security.md` both already document that "Postgres cascade has no reach into Supabase Storage" — that's exactly why `deletePortfolioItem`/`deletePortfolioFile` manually remove Storage objects *before* deleting their DB rows today. If a user row were deleted (bypassing that per-item app logic, e.g. via a future direct `auth.admin.deleteUser()` call), **every remaining file the student never explicitly deleted would become an orphaned object in Storage — unreachable through the app (its owner-scoped row is gone) but still occupying storage and still containing the student's original file bytes.** Any future account-deletion feature must explicitly list-and-remove all of a user's Storage objects (by the `<user_id>/...` path prefix, per `buildPortfolioStoragePath()`'s convention) as its own step, not rely on the DB cascade.
2. **GitHub OAuth tokens.** `connected_identities` rows cascade-delete cleanly, but this audit did not verify in this pass whether the row itself stores a raw token, an encrypted token, or no token at all (the env var `IDENTITY_TOKEN_ENCRYPTION_KEY` strongly implies tokens are encrypted at rest — see the data-inventory report for the authoritative answer). Regardless of encryption, deleting the row removes Avela's *record* of the token but does **not** revoke it on GitHub's side — a deleted Avela account would leave a still-valid OAuth grant sitting in the user's GitHub "Authorized OAuth Apps" settings unless a future deletion flow also calls GitHub's token-revocation endpoint. Flagged as a gap for any future deletion implementation, not fixed here.

**Reversibility/timing (moot today, but for the future deletion feature to address):** because no deletion path exists, there is no current answer to "is deletion immediate or delayed" or "is it reversible" — these are open product questions for whoever builds the feature, not audit findings about existing behavior.

## What must be decided/built before "delete my account" can ship

1. A student-facing entry point (Settings page has a placeholder "more controls coming soon" section — natural location).
2. A confirmation step (re-auth or typed confirmation — not specified anywhere today).
3. A server-side action that: (a) removes all Storage objects under the user's prefix in `student-portfolio`, (b) revokes/attempts to revoke the GitHub OAuth grant if `connected_identities` holds one, (c) calls `supabase.auth.admin.deleteUser()` (server-only, service-role — the same key already read elsewhere per `docs/security.md`, never client-exposed) to let the existing cascade remove every DB row.
4. A decision on immediate vs. grace-period deletion, and on whether integrity/audit rows (`integrity_signals`, rate-limit counters) should survive anonymized rather than cascade-delete, for anti-abuse continuity — this is a product/policy call, not made here.

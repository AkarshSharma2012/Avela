Confirmed from static code review only — see accessibility-coverage-matrix.md for exactly what was and wasn't read. Every item below cites an exact file:line the author verified by reading the source directly; nothing here is a guess about unread code. This supersedes an earlier draft of this file from an earlier pass in this docs folder — that pass explicitly marked `/onboarding`, `/confirm/[token]`, `/verify/[token]`, and `/review/[token]` as "not deep-reviewed"; this pass read them and found two additional confirmed defects there (#3, #4).

Severity taxonomy (as specified for this audit):
- **Critical** — core workflow impossible with keyboard/screen reader; inaccessible auth; focus trapped/lost; essential control has no accessible name.
- **High** — serious contrast failure; form errors not communicated; modal/drawer broken; important content hidden from assistive technology.
- **Medium** — heading/landmark problems; inconsistent focus; small touch targets; unclear link text; status not announced.
- **Low** — minor semantic/descriptive improvements.

**No Critical defects were confirmed this pass.** This is not a claim that none exist — focus-trap behavior, actual keyboard-reachability of every control, and real screen-reader output could not be observed without a browser (see the "Not independently verified" note under #8, and the explicit gaps list in accessibility-coverage-matrix.md).

## High (or worse) — found live during the 10.10B1 final validation pass

### 0. `/verify/[token]` never actually shows its success message — a real Server Action side effect overwrites it with a false "link isn't valid" message, for every user, not just screen-reader users
- **This is a distinct, more severe bug from #1 below, found through live reproduction (not static reading) during the final validation pass.** It affects sighted and keyboard users identically to screen-reader users — the success message is not merely unannounced, it is **never rendered at all**.
- **Where:** `src/lib/verification/actions.ts:503-544` (`resolveVerifierClaim`, the shared implementation behind `confirmVerifierClaim`, `declineVerifierClaim`, and `requestCorrectionFromVerifier`) calls `revalidatePath(...)` twice (lines 541-542) after successfully resolving the claim. `src/components/verification/verifier-response-form.tsx:27-37` (`handleConfirm`) sets client-side `mode: "done"` on the same success response.
- **Reproduction (live, via Playwright against local Supabase, deterministic across two independent runs with fresh tokens):**
  1. A verifier loads a real `/verify/[token]` link and clicks "Yes, this is accurate."
  2. Exactly one `POST` request fires (the Server Action call) — confirmed via a request-count listener, ruling out a double-submission.
  3. Exactly one `framenavigated` event fires immediately after — confirmed via a navigation listener. This does not happen on the sibling `/confirm/[token]` flow (measured identically: 1 POST, **0** `framenavigated` events, and the success text remained stable and unchanged after an extra 4-second wait).
  4. Within under a second, `document.body`'s visible text (script/style tags excluded from the read) is: `"This verification link isn't valid, or has already been used."` — the server-side "not found" branch of `src/app/verify/[token]/page.tsx` (`{!claim ? <p>{error ?? "This verification link isn't valid."}</p> : ...}`), **not** `VerifierResponseForm`'s intended `"Thanks — your confirmation has been recorded."` client state.
  5. The action did succeed server-side — `resolveVerifierClaim` clears the token's `verification_code_hash` (single-use, by design) and records the new verification level *before* the page re-renders. The bug is that the re-render itself, not the underlying action, produces a false "invalid" message about an action that just succeeded.
- **Root cause:** Next.js's App Router Server Action protocol treats any `revalidatePath`/`revalidateTag` call made during a Server Action as an instruction to refresh the invoking route's own Router Cache, regardless of whether the revalidated path is the current route. `resolveVerifierClaim`'s two `revalidatePath` calls target `/portfolio/items/[id]` and `/portfolio` — neither is `/verify/[token]` — but the side effect still forces the *current* `/verify/[token]` page to be re-fetched and re-rendered from the server. Because the token was just single-use-consumed by the same action, that forced re-render's fresh `getVerifierClaim(token)` call now correctly returns "no claim," and the server-rendered fallback replaces the entire tree, including the client component's in-memory `"done"` state. `submitConfirmationResponseAction` (`src/lib/confirmations/actions.ts:119-132`, backing `/confirm/[token]`) has **no `revalidatePath` call at all** — confirmed by reading the full function — which is exactly why that sibling flow does not exhibit this bug.
- **Impact:** Every verifier who confirms, declines, or requests a correction on `/verify/[token]` — the entire audience of this public, no-account page — sees a message that flatly contradicts what just happened ("isn't valid, or has already been used") instead of a confirmation that their response was recorded. This is confusing at best (a legitimate verifier may think their action failed and retry, hit the same now-consistently-invalid token, and give up or contact the student needlessly) and undermines trust in the product. It also makes defect #1 below moot for `/verify/[token]` specifically in one sense (there is no success state at all to announce) and worse in another (a wrong statement is announced/visible instead of a true one).
- **Severity note:** Filed as High-or-worse rather than assigning a final severity — this is a functional-correctness bug with an accessibility-adjacent symptom (nothing here is announced to AT either, since the false message itself has no `role`/`aria-live` — same gap as #1), not a pure WCAG finding, so it sits partly outside this audit's accessibility taxonomy. Recommend the product owner/engineering triage this as at least as urgent as the two High accessibility defects below, likely more so since it affects 100% of users, not just AT users.
- **Not fixed this pass, per audit-first scope and the milestone's explicit instruction not to implement UX decisions.** The smallest likely fix is removing or scoping the two `revalidatePath` calls in `resolveVerifierClaim` so they no longer force-refresh the invoking `/verify/[token]` route (e.g. only revalidating `/portfolio/items/[id]` and `/portfolio` should not need to touch the public verify page's own cache) — but this needs deliberate testing against the dashboard/portfolio pages that those two calls exist to keep fresh, so it is not a same-pass safe fix.

## High

### 1. Reviewer/verifier response forms show a success message that is never announced to assistive technology
- **Where:**
  - `src/components/confirmations/confirmation-response-form.tsx:39-41` — on success, the entire form is replaced by `return <p className="rounded-md border border-border bg-secondary px-4 py-3 text-sm text-foreground">Thanks — your response has been recorded.</p>;` with no `role` and no `aria-live`.
  - `src/components/verification/verifier-response-form.tsx:23-25` — identical pattern: `if (mode === "done") { return <p ...>{doneMessage}</p>; }`, no `role`/`aria-live`.
- **WCAG:** 4.1.3 Status Messages (AA).
- **Impact:** These two forms are the *entire content* of `/confirm/[token]` and `/verify/[token]` — standalone, unauthenticated, no-account pages explicitly designed (per in-file comments) to be usable "under 20 seconds." There is no page navigation/reload to otherwise signal completion. A screen-reader user who taps "Yes, this is accurate" or submits a confirmation gets no announcement that anything happened — the DOM changes silently under them.
- **Contrast with correct pattern already in the codebase:** `src/components/ui/form-message.tsx:14` sets `role={variant === "error" ? "alert" : "status"}` for exactly this kind of message, and is used correctly elsewhere (e.g. `signup-form.tsx`'s post-signup success state). `src/components/portfolio/portfolio-item-form.tsx:461-463` goes further and uses a dedicated `<p role="status" aria-live="polite" className="sr-only">{announcement}</p>` pattern for a "Saved." confirmation. Neither pattern was applied to these two forms.
- **Suggested minimal fix (not applied):** Wrap each success message in `role="status"` (e.g. reuse `<FormMessage variant="success">`), matching the pattern already established in `form-message.tsx`.

### 2. Multi-step wizards change all visible content on every step with no focus move and no announcement
- **Where:**
  - `src/components/onboarding/onboarding-wizard.tsx:166-189` — the step body is a `<div key={draft.step} className="animate-in ...">` that swaps between six different step components (`StepBasicInfo` … `StepReview`) purely via React's key-based remount and a CSS slide animation. No call to `.focus()` on the new step's heading/first field exists anywhere in the file, and no `aria-live` region announces the step change (e.g. "Step 2 of 6: Interests").
  - `src/components/portfolio/capture/guided-capture-flow.tsx:57-63` (`goToCard`) — same pattern for the 5-card guided portfolio-item-creation flow (`CaptureCard` → `DraftCard` → `YourPartCard` → `ProofCard` → `ReadyCard`, each with its own `<h2>` at `capture-card.tsx:59`, `draft-card.tsx:69`, `your-part-card.tsx:52`, `proof-card.tsx:63`, `ready-card.tsx:33`). No focus move, no live-region announcement in this file or its five card children.
- **WCAG:** 4.1.3 Status Messages (AA); adjacent to 2.4.3 Focus Order (A) as SPA-step best practice.
- **Impact:** Both flows are core, required workflows — onboarding is mandatory for every new student (`src/app/(app)/layout.tsx:17-19` redirects to `/onboarding` until `onboarding_completed`), and `/portfolio/new` is the default entry point for building a portfolio. A screen-reader user who presses "Continue" gets no notification that the entire visible page content changed; they must manually re-invoke heading/landmark navigation to discover it, rather than being taken there automatically. A sighted keyboard user's focus visibly stays on the "Continue" button while the content behind it silently changes — workable for them, but disorienting for anyone relying on the screen reader's linear reading order.
- **Suggested minimal fix (not applied):** On each step transition, either move focus to the new step's heading (`tabIndex={-1}` + `.focus()` in a `useEffect` keyed on the step) or add a visually-hidden `aria-live="polite"` region announcing the new step name — the codebase already has the second pattern correctly implemented elsewhere (`portfolio-item-form.tsx:461-463`), it just isn't reused here.

### 5. Onboarding fields set `aria-invalid` without a matching `aria-describedby`, and their error text has no `id` — **Fixed, verified during the 10.10B1 final validation pass**
- **Where (as first read):** `src/components/onboarding/steps/step-basic-info.tsx` — `country` input (lines 64-72: `aria-invalid={Boolean(errors.country)}`, no `aria-describedby`; `<FieldError errors={...} />` at line 72 has no `id`), `city` input (lines 83-90, same gap), `state` input (lines 99-106, same gap). `src/components/onboarding/steps/step-interests.tsx` — `otherInterestText` input (lines 92-101, same gap). Contrast with the correctly-wired `preferredName` field earlier in the same file (`step-basic-info.tsx:32-44`: `aria-describedby={errors.preferredName ? "preferredName-error" : undefined}` + `<FieldError id="preferredName-error" .../>`).
- **WCAG:** 1.3.1 Info and Relationships / 4.1.2 Name, Role, Value (A).
- **Impact:** Because `FieldError` renders with `role="alert"` (`src/components/ui/field-error.tsx:17`), the error text is still announced once, at the moment validation fails (an implicit assertive live region). But since it's not linked via `aria-describedby`, a screen-reader user who tabs away and later returns to a flagged field (e.g. `country`) gets no re-announcement of what's wrong with it — only the field's bare label.
- **Current state:** verified against the working tree — `country`/`city`/`state` in `step-basic-info.tsx` and `otherInterestText` in `step-interests.tsx` now set `aria-describedby` conditionally and pass a matching `id` to `FieldError`, mirroring the `preferredName` pattern. **Recommend a human/AT pass to confirm** the error is re-announced on refocus.

### 7. `aria-describedby` on the portfolio file-upload input referenced an `id` that was never rendered — **Fixed during this audit — verify**
- **Where (as first read):** `src/components/portfolio/file-upload-form.tsx` — the `<input type="file">` had no `aria-describedby`, and the `<FieldError errors={[state.message]} />` rendered below it was never given an `id`. `FieldError` (`src/components/ui/field-error.tsx:15-16`) only sets an `id` on its root `<p>` when one is passed in as a prop.

"portfolio-file-error" : undefined}`, and the `<FieldError>` now has `id="portfolio-file-error"` — the reference now resolves. This appears to fully address the defect. **Recommend a human/AT pass to confirm** the error is re-announced when returning focus to the input after a failed upload.

## Low

### 8. Mobile navigation drawer panel has an unpaired `outline-none` — **Fixed, verified during the 10.10B1 final validation pass**
- **Where (as first read):** `src/components/layout/mobile-nav.tsx:31` — `<Dialog.Popup className="... outline-none ...">`. Every other interactive element found in a repo-wide search of all `outline-none` occurrences in `src/` (~110 matches) pairs it with a `focus-visible:ring-*` replacement; this is the one confirmed exception.
- **WCAG:** 2.4.7 Focus Visible (AA).
- **Impact (explicitly uncertain — flagged as Low rather than Medium/High for this reason):** Base UI's `Dialog.Popup` carries a `tabIndex={-1}` fallback focus target for cases where the panel has no better focusable child, but this panel contains several focusable children (the close button, nav links), so it is plausible initial focus never actually lands on the bare panel itself in practice. Whether this is ever reachable/visible in a real session **could not be confirmed without a browser** — recorded as a genuine code-level finding (the class is objectively missing its usual pairing), not a confirmed user-facing failure.
- **Current state:** verified against the working tree — `mobile-nav.tsx:31`'s `Dialog.Popup` now carries `focus-visible:ring-3 focus-visible:ring-ring/30` alongside `outline-none`, matching the file's own `Dialog.Trigger`/`Dialog.Close` styling. **Recommend a human/AT pass to confirm** visible focus if the bare panel is ever the actual focus target.

### 9. Global `ArrowLeft` keydown handler in the guided-capture flow is scoped only to form-field focus, not all interactive elements
- **Where:** `src/components/portfolio/capture/guided-capture-flow.tsx:78-85` — the window-level `keydown` listener calls `goBack()` on `ArrowLeft` whenever `canGoBack` is true and `document.activeElement` is not an editable element per `isEditableElement()` (line 31: checks only `INPUT`/`TEXTAREA`/`SELECT`/`contentEditable`).
- **WCAG:** No single-key-shortcut SC directly applies (2.1.4 targets printable-character shortcuts; Arrow keys are typically exempt), but this is a real interaction-conflict risk worth recording.
- **Impact:** Narrow. A keyboard user focused on a non-form interactive element inside the flow (e.g. a platform-selection `<button>` in `PlatformPanel`, or any custom widget that itself uses Left-arrow for in-widget navigation) while `canGoBack` is true would trigger an unexpected "go back a step" instead of, or in addition to, the widget's own arrow-key behavior.
- **Suggested minimal fix (not applied):** Broaden `isEditableElement` (or add a second check) to also exclude elements with `role="button"`/`[tabindex]` or elements inside a `role="radiogroup"`/similar composite widget before triggering `goBack()`. Left undone here since it's an interaction-behavior change that could have its own regressions and deserves a deliberate follow-up, not a same-pass patch.

## Not defects — explicitly verified as already correct

- **Dialogs/drawers** (`drawer.tsx`, `confirm-dialog.tsx`, `mobile-nav.tsx`, `osint-consent-dialog.tsx`, `request-verification-dialog.tsx`) are all built on `@base-ui/react/dialog`, which provides focus trapping, Escape-to-close, `aria-modal`, and focus restoration as documented library defaults. No overriding code was found in any of them. **Not independently verified in a live browser this pass.**
- **Auth forms** (`login-form.tsx`, `signup-form.tsx`): correct `<Label htmlFor>`/`id` pairing, `aria-invalid`, `aria-describedby` pointing at `role="alert"` error text, `role="status"`/`role="alert"` `FormMessage` for top-level state — a solid reference pattern the rest of the app only partially follows (see #1, #5, #7 above for where it wasn't).
- **Icon-only buttons**: every one sampled (copy-link, remove-task, remove-evidence, show/hide password, close-drawer, go-back-to-card, remove-proof-item) has an explicit `aria-label`. None found without one.
- **Images**: the app renders zero `<img>`/`next/image` elements anywhere in `src/` — no missing-`alt` defects are possible in the current codebase.
- **Color-only status indicators**: every badge component checked (`eligibility-badge.tsx`, `urgency-badge.tsx`, `application-status-badge.tsx`, and others following the same in-file-documented convention) pairs an icon with text; none rely on color alone.
- **`prefers-reduced-motion`**: `src/app/globals.css:572-581` zeroes all animation/transition durations globally under this media query.
- **Touch target size**: smallest interactive control found (`icon-xs`, 24×24px, `button.tsx:30-31`) meets WCAG 2.2 SC 2.5.8's 24×24 CSS px floor.
- **Public token pages `noindex`**: `/review/[token]`, `/confirm/[token]`, `/verify/[token]` all correctly set `robots: { index: false, follow: false }`.

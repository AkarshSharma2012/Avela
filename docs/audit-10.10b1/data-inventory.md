## AI processing — current state (verify-in-repo finding)

`docs/database.md`'s Milestone 5 section already documents `extraction.ts`'s
"unimplemented LLM-assisted interface placeholder" for opportunity-data
extraction — that placeholder is still just a type/interface shape with no
provider behind it; nothing changed there.

Separately, and **not previously documented in `docs/security.md` or
`docs/database.md`**, a second, portfolio-specific AI module exists at
`src/lib/ai/evidence-grader/`: a real, code-complete "EvidenceSupportGrader"
that would call NVIDIA's hosted Nemotron model
(`https://integrate.api.nvidia.com/v1/chat/completions`) with a
student's evidence excerpts (up to 6 items, 1500 characters each), claim
title/description/role/organization/dates, and the deterministic checks
already run, to produce a JSON assessment of which claim dimensions the
evidence supports. It is:

- **Disabled by default** — `getConfiguredProviderName()` returns
  `"disabled"` unless `AI_EVIDENCE_GRADER_PROVIDER` is explicitly set to
  `nvidia` or `mock`, and the `nvidia` path additionally requires a
  non-empty `NVIDIA_API_KEY`. Neither env var is set anywhere in this
  environment (confirmed — the nvidia-provider.ts file's own header comment
  states "NVIDIA_API_KEY was never configured here... this code path never
  executed").
- **Capped, never a sole source of truth** — its output can never set a
  claim dimension to `externally_confirmed`, only up to `strongly_supported`
  (`aiSupportLevelToClaimDimensionStatus()`), and every caller must treat a
  `{ ok: false }` result exactly like "AI is unavailable."
- **Not found wired into a live Server Action or route in this pass** — the
  only reference outside `src/lib/ai/evidence-grader/` itself is a type
  import in `src/lib/portfolio/capture/types.ts`; no invocation site was
  found in `src/app/`.
- **Text-only** — never sends images/audio/video, per its own header
  comment.

**This is the single most important finding of this report**: a real,
functioning third-party AI integration exists in the codebase (not a mere
placeholder), is currently inert only because of missing configuration, and
was not mentioned anywhere in the existing `docs/security.md`/`docs/database.md`
audit trail. It must be added to any future privacy policy / subprocessor
disclosure the moment `AI_EVIDENCE_GRADER_PROVIDER=nvidia` and
`NVIDIA_API_KEY` are ever set in any environment, including production.

## Data by origin

**Directly supplied by the student**: email (at signup), display name,
grade level, city/state/country, interests, goals, availability,
experience level, opportunity preferences, portfolio entries and their
narrative/structured fields, uploaded files, verifier name/email/organization
they choose to enter, confirmation-request reviewer role/email/display name,
team-collaborator name/email/role, GitHub connect action (student-initiated,
though the identity data itself comes back from GitHub).

**Generated by Avela** (system-computed, not typed by anyone): account ID,
`onboarding_completed`/`onboarding_completed_at`, saved/recommended-opportunity
rows, application-plan status-derived fields, reminder sync rows,
`last_material_hash`, `claim_dimension_results`/events (system-authored
transitions), `integrity_signals`/`integrity_reviews`, `rate_limit_counters`,
verification-level rollups, OSINT check scores/score breakdowns, token
hashes (all token types).

**Imported from third parties**: GitHub profile fields (login, display name,
avatar URL, public-repo metadata) via OAuth/REST once a student connects;
RDAP domain-registration context (registrar/registration date) for a
claim's linked URL or a verifier's email domain; Crossref publication
metadata; YouTube/Vimeo oEmbed video metadata; RSS feed titles — all pulled
only in response to a student-initiated OSINT/verification check, all
keyless (no paid third-party API key configured), all stored as minimal
excerpts/normalized fields, never full page copies (`portfolio_osint_evidence.extracted_fields`,
capped and hashed).

**Supplied by reviewers/confirmers** (people other than the account owner):
a verifier's field-level confirmation responses
(`verification_field_confirmations.response`/`note`), a confirmation-request
reviewer's `response_status`/`response_note`, an Avela-internal reviewer's
`decision`/`reason` on an integrity signal or OSINT check override — all of
this is written through a service-role connection from a narrowly-scoped
server action (the external party never gets an Avela session), never
directly by the reviewer's own client-side write.

**Technical/security data**: `rate_limit_counters` (counts/timestamps only —
no IP/UA, confirmed above), token hashes (sha256, raw token never
persisted, same pattern reused across every token type: review links,
confirmation requests, portfolio/identity/generic-profile possession
challenges, verification links), `connected_identities.access_token_ciphertext`
(AES-256-GCM), `verifier_domain_assessments` (MX/SPF/DMARC/domain-age
context, never a trust score by itself), append-only event/audit tables
(`portfolio_verification_events`, `claim_dimension_events`,
`connected_identity_events`, `portfolio_osint_review_events`).
